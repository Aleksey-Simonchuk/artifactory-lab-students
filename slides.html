Проблема: куда девать результат сборки?

Вы собрали программу. Как передать её коллеге или на сервер?

  • мессенджер / почта — нет версий, нет истории
  • общая папка — «final_v2_FINAL.zip»
  • git — репозиторий раздувается, бинарники там не должны жить

Нужно место, где бинарные файлы хранятся с версиями и контролем целостности.

Что такое артефакт

Артефакт — результат сборки проекта, готовый к распространению:

  • архив .tar.gz, .zip
  • пакет: .jar, .deb, .whl, npm-пакет
  • docker-образ
  • отчёт, документация — что угодно бинарное

Артефакт ≠ исходный код. Исходники — в git, артефакты — в менеджере артефактов.

Почему бинарники не хранят в git

  • git хранит каждую версию каждого файла навсегда — бинарники раздувают репозиторий до гигабайт
  • бинарник нельзя «посмотреть diff» — история git для него бесполезна
  • git не умеет: контрольные суммы, права на скачивание, кэш внешних пакетов, retention

Вывод: git — про исходники, менеджер артефактов — про результаты сборки.

Версионирование: SemVer

У каждого артефакта есть версия. Общепринятый формат — Semantic Versioning:

1.0.0
│ │ └── PATCH — исправления ошибок
│ └────── MINOR — новая функция, совместимость сохранена
└──────── MAJOR — ломающие изменения

Сегодня будем выпускать myapp-1.0.0, myapp-1.0.1…

Менеджер артефактов

Аналогия: git — для исходников, Artifactory — для бинарников.

Что он даёт:

  • хранение артефактов с версиями и историей
  • контрольные суммы и целостность
  • разграничение прав (кто публикует, кто только скачивает)
  • кэширование внешних репозиториев
  • единая точка, откуда CI/CD забирает сборки

Наш стенд: два контейнера

docker compose
→
postgres
база данных
artifactory
:8081 API · :8082 UI
  • Раньше в Artifactory была встроенная база Derby. В свежих версиях её убрали — нужен PostgreSQL.
  • Параметры подключения передаём через переменные окружения в compose-файле.
  • Данные — в томах (volumes): контейнеры можно пересоздавать, данные останутся.

Анатомия docker-compose.yml

services:
  postgres:            # контейнер №1 — база данных
    image: postgres:16-alpine
    environment: [POSTGRES_USER, POSTGRES_PASSWORD, ...]
    volumes: [postgres_data → /var/lib/postgresql/data]
  artifactory:         # контейнер №2 — сам сервис
    image: releases-docker.jfrog.io/jfrog/artifactory-oss
    depends_on: postgres  # ждём базу
    environment: [JF_SHARED_DATABASE_URL=...postgres:5432...]
    ports: ["8081:8081", "8082:8082"]  # наружу:внутрь
    volumes: [artifactory_data → /var/opt/jfrog/artifactory]

Найдите в файле каждый из этих блоков — задание 1 попросит об этом.

Из прошлых занятий нам понадобится

  • tar -czf app.tar.gz -C dir . — упаковать каталог
  • curl — HTTP-запросы из терминала
  • shasum -a 256 file — контрольная сумма
  • конвейеры cmd1 | cmd2, переменные, $1 в скриптах
  • sort -V — сортировка версий

Всё это сегодня соберётся в настоящий пайплайн публикации.

ваши сборки

  • local — ваши собственные артефакты (базовые задания — про него)
  • remote — прокси к Maven Central: первый запрос тянет из интернета, следующие отдаются из кэша мгновенно (pro06)
  • virtual — один URL поверх нескольких репозиториев (pro07)

Контрольные суммы

Хэш (sha256) — «отпечаток» файла. Изменился хоть один байт → сумма другая.

$ shasum -a 256 myapp-1.0.0.tar.gz
63b52a326a651a67bc9b5182e402b3b41d9c596aafce12eb24df20a59ce1203e
  • Artifactory считает суммы при загрузке и отдаёт их в ответе
  • Скачали файл → сверили сумму → уверены, что файл не битый и не подменён
  • Заголовок X-Checksum-Sha256 — проверка прямо при загрузке (task14)

REST API за две минуты

Artifactory управляется HTTP-запросами — значит, из bash, через curl:

МетодСмыслПример
GETполучитьскачать артефакт, список репозиториев
PUTсоздать/заменитьзагрузить файл (-T)
POSTдействиепоиск (AQL)
DELETEудалитьстереть старую версию

Авторизация: curl -u admin:пароль ... (Basic Auth — логин и пароль в каждом запросе).

Promotion: dev → prod

В прод попадает тот же самый бинарник, что прошёл тесты — не пересборка.

  • myapp-dev-local — куда публикует CI
  • myapp-prod-local — куда промоутится проверенная версия
  • Пересобрать «то же самое» нельзя: другой коммит, другая среда сборки — и в проде не то, что тестировали
  • Контроль: sha256 в dev и в prod обязан совпадать (pro08)

Права доступа

  • Принцип минимальных прав: CI-пользователь умеет читать и публиковать, но не удалять (pro04)
  • Удаление — путь к «кто-то стёр прод-артефакт»
  • Пароль в скрипте — только для учебного стенда; в жизни — переменные окружения и секреты CI (pro05)

Правила игры

  • Заходим в папку → читаем README.md → выполняем шаги
  • Команды даны целиком — их нужно просто выполнить
  • Пропуск ____ или пометка ВПИШИТЕ — подставить своё значение: пароль, версию, одно слово
  • В конце каждого README — что сдать в отчёт (скриншот или вывод команды)
  • Застряли — в главном README раздел «Если что-то не работает»

Pro09: пайплайн своими руками

# pipeline.sh — три этапа, как в настоящем CI
./publish.sh "$VERSION"   # 1. собрать и опубликовать
./deploy.sh               # 2. скачать последнюю версию
[[ "$ACTUAL" == "$VERSION" ]]  # 3. проверить, что ехало то
  • set -euo pipefail — упасть на первой ошибке, а не ехать дальше
  • если третий этап не прошёл — весь пайплайн красный, как в Jenkins/GitLab CI

Pro10: GitHub Actions

on: push          # запуск при каждом пуше
jobs:
  build-and-publish:
    runs-on: ubuntu-latest
    steps:
      - checkout
      - упаковать myapp.tar.gz      # ваш tar
      - опубликовать через curl     # ваш curl
  • те же шаги, что вы делали руками, — но выполняет сервер GitHub
  • пароль — в Secrets репозитория, никогда в коде

Итоги

  • Артефакты живут не в git, а в менеджере артефактов
  • Версия + контрольная сумма = доверие к бинарнику
  • local / remote / virtual — три типа репозиториев
  • Всё управляется через REST API — значит, автоматизируется bash'ем
  • В прод едет тот же бит, что тестировался
  • Пайплайн CI — это те же скрипты, что вы написали сегодня
